# Subscription Tracker — sync backend

Минимальный backend для синхронизации подписок между устройствами.
Node.js + Express + Prisma + SQLite. Анонимная авторизация по device_id
(без email/пароля) — MVP-уровень.

## Локальный запуск

```bash
cp .env.example .env
# сгенерировать длинный случайный JWT_SECRET в .env перед первым запуском

npm install
npx prisma migrate dev --name init
npm run dev
```

Проверка: `curl http://localhost:3000/health` → `{"status":"ok"}`

## Деплой (варианты для старта без больших затрат)

- **Railway / Render** — есть бесплатный/дешёвый тир, деплой из git-репозитория,
  переменные окружения (DATABASE_URL, JWT_SECRET) задаются в панели.
  Для SQLite нужен persistent volume (Railway/Render это поддерживают) —
  без него база будет обнуляться при каждом деплое.
- **VPS (от ~300₽/мес)** — youtube-tier VPS + pm2 для процесса + nginx как reverse proxy.
  Больше контроля, чуть больше возни с настройкой на старте.

## Важно перед реальным запуском

1. **JWT_SECRET** — обязательно сменить на длинную случайную строку, не оставлять
   значение из `.env.example`.
2. **HTTPS** — RuStore и Android по умолчанию блокируют cleartext HTTP-трафик
   (`usesCleartextTraffic` выключен) — без HTTPS-сертификата (Let's Encrypt
   через certbot, либо готовый HTTPS у Railway/Render) приложение не сможет
   подключиться к API.
3. **Rate limiting** — сейчас общий лимит 300 запросов/15 мин на весь сервер
   (in-memory, без Redis) — для MVP-нагрузки достаточно, но лимит общий на все IP
   вместе, не по пользователям; при росте стоит вынести в Redis и лимитировать
   по userId.
4. **PostgreSQL при росте** — если пользователей станет много, SQLite (файловая
   БД) станет узким местом при параллельных записях; замена — поменять
   `provider = "sqlite"` на `"postgresql"` в `prisma/schema.prisma` и указать
   `DATABASE_URL` от managed Postgres (Railway/Render/Supabase).
5. **Email/OTP-вход добавлен** — `/auth/request-otp` и `/auth/verify-otp` заменяют
   чисто анонимную модель. Старый `/auth/register` (по device_id) оставлен для
   обратной совместимости, но при первом входе через email на устройстве с уже
   существующим анонимным аккаунтом данные "апгрейдятся" на email-аккаунт
   автоматически — подписки не теряются.
6. **Resend обязателен для реальной отправки писем** — без `RESEND_API_KEY` в
   `.env` коды только логируются в консоль сервера (удобно для локальной
   разработки, но пользователи не получат письмо). Настройка:
   - Зарегистрироваться на resend.com (есть бесплатный тир — 100 писем/день,
     3000/месяц, этого достаточно для старта MVP)
   - Создать API-ключ в разделе API Keys, вставить в `RESEND_API_KEY`
   - Для теста можно отправлять с `onboarding@resend.dev` без верификации домена
     (значение по умолчанию в `.env.example`) — но такие письма чаще попадают
     в спам. Перед реальным запуском лучше верифицировать свой домен в Resend
     (Domains → Add Domain, прописать несколько DNS-записей) и указать
     `EMAIL_FROM=noreply@ваш-домен`
7. **OTP-коды не хешируются** — для MVP с 10-минутным TTL и лимитом 5 попыток
   запроса кода на email это приемлемый компромисс, но при желании усилить
   безопасность стоит хешировать код перед сохранением в БД (как пароль).
